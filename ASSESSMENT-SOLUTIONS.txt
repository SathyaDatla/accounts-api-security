Submission notes and answers

Repository
https://github.com/SathyaDatla/accounts-api-security

The repository contains the implementation, policies, infrastructure examples,
CI workflows, and the supporting documents listed below. Please open the link
in an incognito window before submitting it so you can confirm that anonymous
reviewers can access it. The AWS account numbers and GitHub identities in the
examples are placeholders; they need to be replaced before a real rollout.

How I approached the scenario

I assumed accounts-api runs in the accounts namespace of a shared EKS cluster
in ap-south-1. RDS is private, and the application uses its own database login
rather than the RDS master credential. The pod uses IRSA, and External Secrets
Operator retrieves runtime values from AWS Secrets Manager. The application
does not need access to the Kubernetes API. I used Cilium for workload network
policy. The KYC hostname, stream broker names, AWS account, subnet IDs, KMS key,
and security groups are examples that would need environment-specific values.

Part 1: Build and reviewer entry point

Upload README.md. It explains the local checks and the optional Terraform and
kind workflows. To run the policy checks, install Python 3 and Conftest, open
PowerShell in the repository root, and run:

  Set-ExecutionPolicy -Scope Process Bypass
  .\setup-lab.ps1

The script checks both passing and intentionally failing Rego fixtures, then
checks the waiver register. If Kyverno is installed, the script runs its
admission tests as well. For Terraform, run:

  terraform -chdir=infra/terraform init -backend=false -input=false
  terraform -chdir=infra/terraform validate

These checks do not need AWS credentials. I would not run terraform apply for
this exercise. The optional `-CreateKindCluster` switch creates a local cluster
and checks connectivity; it does not deploy the example workload.

Section 1: Threat model

Upload docs/threat-model.md. It contains the trust-boundary diagram and the
full threat model. My five highest-priority risks are:

1. Code execution in the API. An attacker could reach the service through a
   vulnerable endpoint or dependency, then access data and credentials the
   process is allowed to use or try to pivot within the shared cluster. I
   reduced the pivot paths with a non-root workload, no host access, narrow
   IAM, restricted egress, and a Falco rule for unexpected shell execution.
   An attacker can still read data the API legitimately handles.
2. A compromised maintainer or release workflow. An attacker may try to
   change source or CI and publish an unauthorized image. Reviewed changes, a
   protected production environment, scoped OIDC, immutable ECR tags, image
   signing, and an SBOM attestation make that path harder and more visible.
3. A secret or customer-data leak. Process compromise, debug output, or an
   exception could expose a credential or PII. Secrets Manager delivery, a
   narrow pod role, rotation, and redaction before log serialization reduce
   that risk. They cannot protect a secret already read into compromised
   process memory.
4. A pivot from another workload in the shared cluster. An attacker may try
   to use host resources, Kubernetes credentials, or open network paths. The
   workload has no host namespaces or hostPath mounts, no mounted API token or
   RBAC grant, and default-deny egress. I still treat a namespace as a useful
   boundary, not as hard isolation.
5. Database exposure or missing incident evidence. A public database rule
   could expose account records, while incomplete audit records make an
   incident difficult to reconstruct. The example keeps RDS private and
   encrypted, restricts ingress to the app security group, enables backups,
   and stores validated multi-region CloudTrail logs with retention controls.

I would not spend the first week blocking every low-severity dependency alert.
Reachability and likely impact matter. Critical and high findings block; lower
severity findings need an owner and a due date while the team tunes its signal.

Section 2: Build and release integrity

Upload .github/workflows/release.yml and
infra/iam/github-oidc-trust.json.

The release workflow uses GitHub Actions OIDC to assume the AWS release role.
It tags the image with the commit SHA, creates an SPDX SBOM, publishes the SBOM
as a Cosign OCI attestation, scans the image, signs it keylessly, and verifies
the signature and attestation. The ECR repository is configured with immutable
tags, so a published commit tag cannot be overwritten.

The trust policy requires the token audience to be sts.amazonaws.com and the
subject to be repo:bank/accounts-api:environment:production. That scope denies
other repositories, refs, and environments from assuming this role. The
identity is illustrative and must be changed to the real repository and
production environment before use.

I chose keyless signing to avoid maintaining a long-lived private signing key.
The trust roots are the GitHub OIDC identity and Sigstore's certificate
transparency and verification roots. The signature ties an image digest to an
authorized workflow identity; it does not prove the source is safe, the
workflow was uncompromised, or a reviewer understood every line of code.

Section 3: Pipeline gates and the waiver path

Upload .github/workflows/security-gates.yml, waivers/waivers.json,
scripts/check_waivers.py, waivers/README.md, and docs/break-glass.md.

I use Trivy for dependency and image scanning because one tool keeps the
pipeline manageable, though it does not provide reachability analysis. Semgrep
provides static analysis. Gitleaks scans the complete checkout history; the
workflow fetches full history with `fetch-depth: 0`. Checkov provides broad
Terraform coverage, while the Rego policies capture the specific invariants I
want these fixtures to protect.

On day one, leaked secrets, critical or high vulnerability findings, invalid
or expired waivers, failed policy fixtures, and failed required IaC checks
block a merge. High-confidence Semgrep findings block too. Medium and low
dependency findings warn and get an owner and due date. I would review the
first month of results and tune narrow noisy rules first; I would promote
additional warning classes only when the false-positive rate is low enough
that engineers still trust the gate. My target is fewer than five percent
reviewed false positives before promotion.

Waivers live in waivers/waivers.json. Each record needs a finding ID, a reason,
a compensating control, an owner, an approver, a tracking issue, and UTC
creation and expiry times. The checker fails on missing fields, bad timestamps,
excessive duration, or expiry. A normal waiver can last at most 30 days; a
break-glass waiver can last at most four hours. In GitHub, I would require a
verified signed commit, two approvals, platform CODEOWNERS review, no
self-approval, and no admin bypass for changes to the waiver file. Those are
organization settings and cannot be enforced by this repository alone.

For a production-down incident, the incident commander opens an incident
record. The platform on-call engineer and service owner approve only the
smallest required exception. The production environment review, OIDC, image
signature, and audit logging stay enabled. The release uses a short-lived role
session tagged with the incident ID and an immutable image digest. The waiver,
approvals, GitHub audit events, and CloudTrail records go into the incident
trail and the security account. After recovery, remove the waiver, rotate any
possibly exposed credentials, and review the incident on the next business day.

Section 4: Review and remediate

For the workload and RBAC deliverable, upload:
  k8s/base/deployment.yaml
  k8s/base/rbac.yaml
  policy/rego/kubernetes.rego
  k8s/fixtures/bad-deployment.yaml
  k8s/fixtures/bad-role.yaml
  k8s/kyverno/kyverno-test.yaml

I ranked host access first because hostNetwork, the Docker socket, and host
logs can turn an API exploit into a node-level or cross-workload incident. The
fixed Deployment removes those mounts and host namespaces, runs as UID/GID
10001, uses RuntimeDefault seccomp, drops all capabilities, prevents privilege
escalation, and has a read-only root filesystem. The mutable `:latest` image
is replaced by a sha256 digest. The service has no Kubernetes API use case, so
there is no Role or RoleBinding and its service-account token is not mounted.
The Rego rules and negative fixtures keep the important defects from silently
returning.

For Terraform and its policy, upload:
  infra/terraform/main.tf
  infra/terraform/variables.tf
  infra/terraform/outputs.tf
  policy/rego/terraform.rego
  infra/terraform/fixtures/good-db.yaml
  infra/terraform/fixtures/bad-db.yaml

The most urgent Terraform issue is public PostgreSQL access, especially with
0.0.0.0/0 ingress. The fixed configuration makes RDS private and permits port
5432 only from the application security group. It enables KMS encryption,
14-day backups, deletion protection, Multi-AZ, and a final snapshot. The
CloudTrail example is an organization trail across regions, validates log
files, includes global service events, and writes to a versioned, encrypted,
public-access-blocked bucket with 365-day compliance-mode object lock.

For the pod IAM deliverable, upload infra/iam/accounts-api-role-policy.json and
infra/iam/DENIES.md. The policy permits reads of only the named Secrets Manager
secret and KMS decryption only through Secrets Manager for that secret's
encryption context. It denies the broad AWS actions the original NotAction
allow could have permitted if the empty Resource had effectively been `*`.

Section 5: Admission, runtime, and egress

Upload k8s/kyverno/policies.yaml, k8s/kyverno/kyverno-test.yaml,
k8s/fixtures/bad-deployment.yaml, runtime/falco/accounts-api.yaml,
k8s/base/network-policy.yaml, and docs/runtime.md.

I would start Kyverno in Audit for the shared cluster and scope the initial
review to accounts. I would promote accounts-api to Enforce after 14
consecutive days without unexplained violations, service-owner signoff, an
exception inventory, and a canary plus rollback rehearsal. That gives the
platform team evidence before a policy can disrupt the other teams.

The custom Falco rule looks for a shell or common network utility starting in
the accounts-api container, where a normal Go HTTP service should not need
one. Falcosidekick sends the event to the central security event bus, and the
platform on-call engineer and service owner are paged. The alert carries the
time, cluster, namespace, pod, container, image, process, parent, user, and
node; I leave command arguments out because they could contain secrets.

The first response is to preserve pod, node, EKS audit, flow, and process
evidence and record the image digest and request IDs. With the incident
commander, the responder then isolates egress and replaces pods only after
preserving evidence. Finally, they revoke or rotate the database and KYC
credentials and review CloudTrail, RDS, and audit records for access.

Cilium allows the KYC provider on TLS port 443, the private database on 5432,
and private stream brokers on 9094. DNS is allowed only for those names, and
the namespace default-deny policy blocks the rest. This depends on Cilium's
DNS proxy/FQDN policy and real environment hostnames. It cannot prevent misuse
of an allowed endpoint, all traffic behind a shared CDN address, or DNS
tunnelling through permitted DNS.

Section 6: Secrets and data protection

Upload k8s/base/secret-store.yaml, docs/rotation.md,
docs/log-redaction.md, and docs/encryption.md.

AWS Secrets Manager is the source of truth and uses a customer-managed KMS
key. External Secrets Operator uses a narrowly scoped IRSA service account to
write a namespaced Kubernetes Secret, which the pod mounts read-only. The
repository holds secret names and property references, never credential
values. RDS manages its master password; the application uses a separate,
least-privilege database login.

I would rotate the application database login every 30 days and the KYC key
every 90 days. For an incident, the target is to revoke an exposed value
within five minutes and move all consumers to a replacement within 15 minutes
of declaring the incident. IRSA has no static key to rotate; on suspected role
abuse, restrict the role and terminate affected pods immediately, then verify
session duration and revocation behavior in the production account. The RDS
master credential is managed separately and is never mounted in the app pod.
For routine rotation, publish the new value, refresh the mounted Secret, roll
the pods, confirm new connections, and only then revoke the old value. Rotation
cannot undo a credential that an attacker has already copied.

I would redact authorization and cookie headers, tokens, passwords, connection
strings, names, email, phone, IBAN/account numbers, card PAN/CVV, KYC payloads,
and request and response bodies before serializing application logs. I would
use an allowlist for request ID, route template, status, latency bucket,
service version, and pseudonymous actor ID, and apply the same policy to
ingress logs. Timing, route, status, response size, and correlation still
leak. New fields, exception messages, traces, heap dumps, or provider logs can
bypass this layer. The scenario only includes last-four card data; I would not
store full PAN/CVV or log last-four.

For encryption, RDS, ECR, Secrets Manager, and CloudTrail use customer-managed
KMS keys controlled by the platform account, and client, database, and
provider connections use TLS. This helps with lost media and snapshots, but it
does not protect plaintext from an authorized compromised process or an overly
broad KMS principal.

Part 2: Decisions and trade-offs

Upload docs/decisions.md. I would defend three decisions in particular. First,
publish once, use immutable commit tags, and deploy by digest; signing and an
SBOM improve provenance, but do not prove the code is safe. Second, make
non-root execution, no host access, and digest-pinned images the workload
baseline, while staging cluster-wide admission from Audit to Enforce. This
avoids surprising other teams, at the cost of accepting a short period in
which violations are reported rather than blocked. Third, use Cilium for
name-based egress instead of maintaining KYC provider IP ranges by hand. That
is easier to operate, but an attacker can still misuse an allowed hostname or
abuse permitted DNS.

On day one, full-history secret scanning, expired-waiver checks,
critical/high vulnerability findings, high-confidence Semgrep findings,
required IaC checks, and failed policy fixtures block. Medium and low
dependency findings warn and receive an owner and due date. Kyverno begins in
Audit; the evidence to promote it is 14 clean days, owner signoff, an exception
inventory, and a rollback rehearsal.

If an attacker gets RCE in the API, they can reach data and credentials the
service is authorized to use. They should not get the node Docker socket, host
logs, Kubernetes API permissions, broad AWS actions, or arbitrary egress.
EKS audit, Cilium flows and DNS, Falco, CloudTrail, RDS, and ALB/WAF logs
should help reconstruct activity when exported to central retention. We will
not see every in-memory read, and valid API calls may look normal.

If a maintainer account and workflow are compromised, the attacker may change
source or try to publish a malicious image. Required review, checks, the
protected production environment, scoped OIDC, immutable tags, and signature
verification constrain that path. GitHub audit history, the signed image and
attestation, CloudTrail role sessions, and the registry digest provide
evidence. If an environment approver or organization administrator is also
compromised, these checks lose much of their value. GitHub audit export must
be configured outside this repository.

One gap I accept for this exercise is slow scraping through valid customer
sessions. It may look like ordinary traffic. Closing it would require
per-customer behavior baselines, rate analysis, and a staffed response
function; that is a product and operations investment, not just another alert.

The controls with the clearest regulatory value are:
  - EKS and RDS in ap-south-1 (assumption): data residency.
  - Validated multi-region CloudTrail with locked retention: audit integrity
    and retention.
  - Encrypted RDS and retained backups: confidentiality and recovery.
  - Narrow pod IAM and reviewed, expiring waivers: access review.
  - No full PAN/CVV storage or logging: cardholder-data scope.
  - A named alert owner and responder runbook: breach readiness.

I cut live cloud deployment, a full business API, DAST, and organization-wide
GuardDuty configuration. On Monday, I would canary admission and egress in
the owned namespace, centralize the logs in the security account, and test the
on-call path end-to-end.

Additional notes for reviewers

This is a local reference implementation, not evidence that controls have
been deployed to AWS or enforced in a live cluster. The Go service is a small
health-only stand-in. Before production, replace the illustrative AWS account
IDs, GitHub identities, hostnames, and network IDs. Also configure and verify
GitHub branch protection, CODEOWNERS enforcement, production environment
reviewers, signed-commit requirements, audit export, and admin bypass rules;
those controls cannot be created by repository files alone.
